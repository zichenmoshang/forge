# 流程设计

## 整体流程

```
PRD文档
  │
  ▼
阶段1：需求解析与澄清
  │
  ▼
阶段2：用户故事拆解
  │
  ▼ 【弱介入窗口：AI自检通过即放行，30秒内人工可介入】
阶段3：前端技术方案设计
  │   ├─ 技术栈检测/建议
  │   ├─ Figma 设计数据提取
  │   ├─ 页面/路由/组件树设计
  │   ├─ 状态管理/数据模型设计
  │   ├─ API 契约生成（Agent 内部检索历史知识库）
  │   ├─ 异常与边界场景补齐
  │   └─ 非功能需求落地方案
  │
  ▼
阶段4：技术方案评审（评审 Agent，多轮对话，弱模式）
  │   不通过且为方案性问题 → 回退阶段3（对话循环内修改不算回退）
  │
  ▼ 【硬卡点：API 契约确认（ADR-014：评审通过后再确认，确认的是稳定版契约）】
阶段5：TDD 代码生成（混合模式）
  │   按用户故事逐条：
  │   ① 基于 AC + API 契约生成测试用例
  │   ② Mock 接口数据
  │   ③ 沙箱运行测试 → 确认失败
  │   ④ 生成最小实现
  │   ⑤ 运行测试 → 确认通过
  │   ⑥ 重构
  │   真实项目级集成验证
  │
  ▼
阶段6：代码 CR 与自我验证（CR Agent，多轮对话）
  │   不通过 → 对话循环内 Coder 修改（代码问题）或回退阶段3（方案问题）
  │
  ▼
阶段7：PR 交付
  │   创建分支 → 生成/修改代码 → 构建验证 → 创建 PR
  │
  ▼ 【硬卡点：最终交付确认】
交付：PR 链接 + 交付说明（人工确认后完成）
```

## 各阶段详细说明

### 阶段1：需求解析与澄清

**输入**：PRD 文档、埋点需求、全局需求、历史知识库（v2：历史澄清问题、全局需求清单、技术规范）

**做什么**：
- 解析 PRD，提取业务目标、角色、功能点、业务规则
- 明确非功能需求（性能、兼容性、安全、无障碍、国际化等）
  - AI 提示常见项，人工确认具体指标
- 识别缺失项、歧义点、矛盾点，生成澄清问题清单
- 多轮澄清问答，直到需求充分
- 检查全局需求是否缺失（如登录体系、权限），缺失则提出
- 需求冻结

**输出**：结构化需求文档

**质量门禁**：
- 业务目标明确
- 角色完整
- 功能点无遗漏
- 业务规则无歧义
- 非功能需求已明确
- 全局需求已覆盖

### 阶段2：用户故事拆解

**输入**：冻结后的结构化需求、历史知识库（v2：历史故事结构、AC 写法模式、故事规范）

**做什么**：
- 按角色+场景拆成用户故事（As a... I want... So that...）
- 每条配验收标准（Given/When/Then）
- 标注优先级、依赖关系
- 非功能需求映射到相关故事或单独标记

**输出**：用户故事列表 + 验收标准 + 故事地图

**质量门禁**：
- INVEST 原则检查（独立、可协商、有价值、可估算、小、可测试）
- 每条故事有可验证的 AC
- 故事间依赖关系明确

**弱介入窗口**：AI 自检通过后设置 30 秒等待窗口，窗口内人工可介入修改或要求重新生成；超时自动进入下一阶段。

### 阶段3：前端技术方案设计

**输入**：用户故事 + Figma 设计稿 + 历史知识库 + 现有代码索引

**做什么**：

1. **技术栈检测/建议**
   - 已有项目：自动读取 package.json/tsconfig/eslint 确定技术栈
   - 新项目：检索团队约束 + 项目特点生成建议，弱模式自动采用

2. **Figma 设计数据提取**
   - 通过 Figma API 提取布局、样式、组件、设计 token（颜色/字号/间距）
   - 用于组件设计和 UI 生成

3. **页面/路由/组件树设计**
   - 页面结构与路由设计
   - 组件树与组件职责划分
   - 检查现有代码仓库，标记可复用组件

4. **状态管理设计**
   - 全局状态 vs 局部状态的边界
   - 服务端状态与客户端状态的区分
   - 具体方案明确到组件级

5. **数据模型设计**
   - 页面数据结构
   - 类型定义

6. **API 契约生成**
   - DesignAgent 内部检索历史知识库（ADR-014：检索由 Agent 自主完成，ContextManager 不预检索），优先复用已有接口模式
   - 新增接口标记"新增"
   - 包含请求/响应/错误码
   - 注意：此处只生成，**不确认**；API 确认硬卡点位于阶段4评审通过之后

7. **异常与边界场景补齐**（checklist 驱动）
   - 空状态、加载中、加载失败、网络异常
   - 表单校验、重复提交、并发冲突
   - 权限不足、数据为空、超长文本
   - 边界值和极端情况

8. **非功能需求落地方案**
   - 性能：虚拟滚动、懒加载、代码分割
   - 错误监控：try/catch 手动上报（默认规则）
   - 兼容性、无障碍、国际化方案

9. **目录结构与文件组织**

**输出**：前端技术方案设计文档

**质量门禁**：
- 每条用户故事的 AC 都能映射到具体组件/接口/状态
- 异常场景完整
- 非功能需求有落地方案
- （API 契约确认在阶段4之后，不属于本阶段门禁）

### 阶段4：技术方案评审（多轮对话）

**输入**：前端技术方案

**评审维度**（Reviewer Agent）：
- 覆盖度：所有故事 AC 是否被方案覆盖
- 异常完整性：边界场景是否齐全
- 接口一致性：契约是否自洽、与历史模式一致
- 架构合理性：有无过度设计或遗漏
- 状态管理：全局/局部边界是否合理
- 非功能需求：是否有对应措施

**多轮对话机制**：

Reviewer 和 Designer 在本阶段内进行多轮对话，直到通过或达到终止条件：

```
第1轮：Reviewer 评审方案
  ├─ approve → 通过，进入阶段5
  ├─ request_human → 暂停等人工
  └─ request_changes → Designer 修改方案 → 第2轮
第2轮：Reviewer 评审修改后的方案
  ├─ approve → 通过
  ├─ request_human → 暂停
  └─ request_changes → Designer 修改 → 第3轮
第3轮：最终评审
  └─ 仍未通过 → 达到最大轮次，暂停等人工
```

**配置**：
- 最大轮次：默认 3 轮（可配置 `maxReviewRounds`）
- 通过标准：verdict=approve 且无 blocking 级别问题
- 每轮后弱介入：默认关闭，可配置 `interruptAfterEachRound`

**输出**：评审意见（结构化）+ 评审对话历史 + 最终方案版本

**处理**：
- 通过 → 弱介入窗口（30秒内人工可介入要求回退）→ 进入 API 契约确认硬卡点
- 人工介入 → 人工可修改方案后继续，或要求回退阶段3
- 达到最大轮次 → 暂停等人工决策

### 阶段4.5：API 契约确认（硬卡点）

**位置决策（ADR-014）**：API 确认从"方案生成后、评审前"调整到"方案评审通过后"。原因：若先确认再评审，评审一旦要求修改 API，人工确认就作废需要二次确认；评审后确认的是经过 AI 评审的稳定版本。

**输入**：评审通过的技术方案（含 API 契约）

**做什么**：
- 人工审阅 API 契约（请求/响应/错误码、接口粒度、与后端的一致性）
- 人工可直接修改契约文本，或要求回退阶段3重新设计
- 确认后契约冻结，作为阶段5 TDD mock 数据和测试用例的确定依据

**出口**：
- 确认 → 进入阶段5编码
- 发现方案性问题 → 回退阶段3（评审与确认随后重新执行，不能用旧确认覆盖新产物）

### 阶段5：TDD 代码生成

> ✅ **v1 已实现（方案丙：可替换工具层）**：CodingAgent 对单故事执行 red（只产测试+mock，工作区内运行且必须失败，反假测试）→ green（产最小实现转绿，失败在 maxGreenAttempts=5 内带失败信息修复）；Harness.runCodingPhase 按依赖拓扑逐故事编排、单故事失败不阻塞、聚合 CodingPhaseResult 并按 all-success/partial/all-failed 三分支出口（#40）。工具层为接口抽象：CLI 默认 **LocalSubprocessTestRunner（#83 已落地）**——把工作区落盘到项目 `.sandbox/` 临时目录，真实调用 vitest 子进程执行，解析 JSON 输出还原真实通过/失败/失败原因（red 无实现 → 真实 import 解析失败；假测试不引用实现 → 真实全绿被 RED_SHOULD_FAIL 拦截；实现有 bug → 真实断言错误信息回流给修复循环）。vitest 不可用/超时时自动降级 StaticTestRunner（静态推断并明确标注"降级静态推断"；fallbackToStatic=false 则返回环境失败）。`--test-mode static` 可显式切回静态推断快速通道。代码全文暂存于 GeneratedFile.content，真实落盘随交付阶段。

**输入**：技术方案 + 用户故事 AC + API 契约

**混合模式**：
- 单元测试在沙箱运行（快速反馈）
- 集成级 mock 测试在真实项目运行（保证环境一致）

**按用户故事逐条循环**：
1. 基于 AC + API 契约生成测试用例
2. 基于 API 契约生成 mock 数据
3. 沙箱运行测试 → 确认失败（红）
4. 生成最小实现代码
5. 运行测试 → 确认通过（绿）
6. 重构

**测试质量要求**：
- 每个 AC 必须对应至少一个断言具体业务逻辑的测试
- 断言必须有意义，不允许"假测试"
- 覆盖正常值、边界值、异常路径

**输出**：测试代码 + 实现代码 + 编码阶段汇总（CodingPhaseResult）

**单个故事失败处理**：
- 测试失败重试达上限（默认5次）→ 标记该故事失败，记录原因
- 继续下一个故事，不阻塞整体流程

**CODING 出口判定（ADR-014 明确三种情况）**：
- 全部故事成功 → 直接进入阶段6 CR
- 部分成功部分失败 → 触发弱介入窗口，人工决定：①带着失败故事继续 CR（交付时列为 incomplete）；②回退阶段3；③暂停排查
- 全部失败 → FAILED，通知人工（不再进入 CR）

阶段6 CR 的对象是成功生成的故事；失败故事不参与 CR，最终在交付说明中列为 incompleteStories。

### 阶段6：代码 CR 与自我验证（多轮对话）

> ✅ **v1 已实现（复用 #42 多轮对话模式）**：ReviewAgent 扩展 review-code 分支（CR 维度：方案一致性/规范/逻辑/异常/安全/可维护性/测试有效性/设计还原度文本核对），与 CodingAgent.revise（针对性修改+重跑 TestRunner+逐项 issueResponses）在 CODE_REVIEWING 阶段内多轮对话。Harness.runCodeReviewDialog 按轮次循环：Reviewer CR→approve/request_human/request_changes→Coder 修订受影响故事→下一轮；第2轮起对上轮 open issue 逐项 verification 闭环（遗漏判无效重试）；只有 blocking 问题才触发 request_changes（非 blocking 问题程序化降级为 approve）。产物 code-review + code-review-history。出口：approve→进入阶段7交付（DeliveryAgent 执行）；request_human/达最大轮次→暂停等人工，resume 续跑或接受当前版本。CR 只针对 success/partial 故事，failed 故事不参与并在交付说明列 incomplete。设计还原度图片比对留 v2。

**输入**：生成的代码 + 技术方案

**CR 维度**（Reviewer Agent）：
- 与技术方案一致性
- 代码规范、逻辑正确性
- 异常处理是否到位
- 安全检查（XSS、硬编码密钥等）
- 可维护性、重复代码
- 测试有效性审查（测试是否真实验证了 AC）
- 设计还原度（图片比对 Figma）

**多轮对话机制**：

与阶段4相同，Reviewer 和 Coder 在本阶段内多轮对话：

```
第1轮：Reviewer CR 代码
  ├─ approve → 通过
  ├─ request_human → 暂停等人工
  └─ request_changes → Coder 修改代码 + 重跑测试 → 第2轮
...
达到最大轮次仍未通过 → 暂停等人工
```

**输出**：CR 意见 + CR 对话历史 + 最终代码版本

**处理**：
- 代码问题 → Coder 在对话循环内修复 → 重新 CR（不回退阶段5）
- 方案性问题 → 回退阶段3修改方案
- 通过 → 弱介入窗口（30秒内人工可介入要求回退）→ 进入阶段7

### 阶段7：PR 交付

**输入**：通过 CR 的代码

**做什么**：
1. 创建特性分支
2. 按交付场景处理：
   - 新项目：初始化项目结构 + 配置 + 生成代码
   - 新模块：在现有项目中新增目录和文件
   - 代码修改：定位并修改现有文件
3. 项目级构建/测试验证
4. 自动生成 PR 描述（关联需求、用户故事、测试结果、CR 记录）
5. 创建 PR

**输出**：PR 链接 + 交付说明

**最终交付确认** ← 硬卡点：
- PR 创建后进入等待状态，人工确认后流程完成
- 人工可要求修改（回退到对应阶段）或确认完成

> ✅ **v1 已实现**：DeliveryAgent 执行完整交付流程——场景判定（自动推断目标项目状态：新项目/新模块/代码修改，可显式指定）→ 新项目初始化（React+TypeScript+Vite 基础结构）→ 代码落盘（GeneratedFile.content → 目标项目文件，新建/覆盖）→ 构建验证（自动检测包管理器+构建命令，失败记录 knownIssues）→ Git 本地操作（init/创建分支 feature/forge-{instanceId}/add/commit，v1 不远程 push）→ PR 描述 LLM 生成（关联需求/故事/测试/CR/变更，LLM 失败时兜底模板）。工具层为接口抽象：FileSystemClient/GitClient/BuildRunner，v1 默认实现调用本地 CLI，可注入替换。Harness 编排：DELIVERING → DeliveryAgent 执行 → 保存 delivery 产物 → 推进到 DELIVERY_CONFIRMATION 硬卡点 → 人工确认后 COMPLETED。远程 PR 创建（GitHub/GitLab API）留 v2。

## 回退机制汇总

| 发现问题的阶段 | 回退到 | 触发条件 |
|---|---|---|
| 阶段2 故事拆解 | 阶段1 | 需求描述不足，无法拆出可测试的故事 |
| 阶段3 方案设计 | 阶段2 | 某故事 AC 模糊/矛盾/不可实现 |
| 阶段4 方案评审 | 阶段3 | 评审中发现方案性问题，人工要求回退（多轮对话内修改由 Designer 直接完成，不回退） |
| API 确认 | 阶段3 | 人工确认时发现 API 方案缺陷（回退后评审、确认重新执行） |
| 阶段5 编码 | 阶段3 | 写代码时发现方案不可行或遗漏关键场景 |
| 阶段6 CR | 阶段5 / 阶段3 | 代码问题在对话循环内修复；方案性问题回退阶段3 |

**回退规则**：
- 每次回退修正后，从修正点重新往下走，后续产物全部重新生成（v1 不做增量补丁）
- 回退目标状态之后的**所有确认和评审环节必须重新执行**（不能用旧确认覆盖新产物）
- 每次回退流程版本号 currentVersion +1（产物自身版本单调递增，见"版本号体系"）
- **回退成本预警（ADR-014）**：人工触发回退前，Harness 自动计算并展示将废弃的产物规模（如"回退到阶段3将废弃 N 个故事的代码、M 个文件"），由人工确认后执行
- v1 之后考虑增量更新（只重新生成受影响的故事/组件，需要影响面分析能力）

**评审阶段的内部循环 vs 回退**：
- 评审阶段内的多轮对话（Designer 修改方案、Coder 修改代码）**不是回退**，是同一状态内的迭代，产物版本 +1
- 只有人工明确要求回退，或发现方案性问题需要重新设计时，才回退到阶段3

## 流程取消

- 人工可在任意非终态主动取消流程，进入 `CANCELLED` 终态（ADR-014 新增），不可恢复
- 已生成产物保留用于审计，但不再继续执行；如需重新处理，创建新实例
- 终态共三个：COMPLETED（正常完成）、FAILED（兜底失败）、CANCELLED（人工取消）

## 版本号体系（ADR-014 明确）

系统中存在两套独立版本，不可混用：

| 版本 | 字段 | 递增时机 | 用途 |
|---|---|---|---|
| 流程版本 | `PipelineState.currentVersion` | 每次状态机回退 +1 | 标识"第几轮流程"，判断下游确认/评审是否需要重新执行 |
| 产物版本 | 各产物的 `version`（如 FrontendDesignDoc.version） | 每次重新生成或评审内修改 +1，单调递增，不随回退重置 | 标识产物迭代次数，评审历史记录最终通过的产物版本 |

示例：方案 v1→评审修改2轮到 v3→回退（流程版本 v2）→重新生成方案为 v4（不重置为 v1）。

## 兜底策略

具体策略在遇到时定义，基本原则：
- 每个阶段有最大重试次数
- 达到上限后：停下来等人工 / 降级交付已完成部分并标记风险
- 部分交付时 PR 包含已完成内容，未完成部分明确标记

## 非功能需求处理
