# 知识库方案

## 定位

历史知识库是**团队级中心化**的通用知识服务，跨项目复用，用于需求澄清、故事拆解、技术方案设计三个阶段参考已有模式、复用接口定义、遵循团队规范。

与现有代码索引的区别：
- **知识库**：跨项目通用知识，回答"通常怎么做""团队规范是什么"
- **代码索引**：当前项目特定代码，回答"这个项目里已经有什么"

## 核心原则

1. **不做模型训练（fine-tuning）**：代码更新频繁，训练成本高周期长，可解释性差
2. **代码反解析为主**：从已上线代码中提取知识，代码是真相来源
3. **无人工打标**：程序化提取元数据 + 语义检索 + 查询时动态增强
4. **自动化质量保证**：来源过滤 + 交叉验证 + 规则校验 + 使用反馈
5. **团队级中心化部署**：统一服务，多项目共享，避免重复建设

## 知识内容

| 知识类型 | 来源 | 提取内容 | v1 | v2 |
|---|---|---|---|---|
| API 接口 | 代码中 api 目录、请求封装 | 接口路径、method、请求参数、响应类型、错误码 | ✅ | - |
| 组件用法 | 组件源码 + 引用处 | 组件名、props、类型、默认值、事件、使用示例 | ✅ | - |
| 数据模型 | types/interfaces 目录 | 模型名、字段、类型、嵌套关系 | ✅ | - |
| 技术方案 | 已合并 PR 描述、历史方案文档 | 架构决策、页面方案、交互模式 | ✅ | - |
| 代码规范 | 配置文件、规范文档 | 目录约定、命名规范、写法约定 | ✅ | - |
| 异常处理模式 | 全局拦截器、错误边界、hooks | 请求重试、错误提示、loading 管理 | ✅ | - |
| 高频代码模式 | 全量代码扫描归纳 | 列表页通用写法、表单通用写法 | ✅ | - |
| 历史澄清问题 | 已完成需求的澄清日志 | 澄清问题、回答、所属功能模块 | ❌ | ✅ |
| 历史故事集 | 已完成需求的用户故事 | 故事结构、AC 写法、依赖关系 | ❌ | ✅ |
| 技术文档 wiki | 飞书文档 | 团队技术规范、架构决策、最佳实践、技术选型 | ❌ | ✅ |
| 全局需求清单 | 团队维护的标准全局需求 | 登录、权限、错误处理、埋点等标准项 | ❌ | ✅ |

## 知识库在各阶段的使用方式

### 阶段1：需求澄清

**核心价值**：用历史经验补全澄清盲区，避免"该问的没问到"。

| 使用场景 | 知识库提供什么 | 举例 |
|---|---|---|
| 历史类似需求的澄清问题 | 之前做同类功能时踩过的坑 | 上次做"头像上传"漏问了裁剪比例和文件大小限制，这次自动提示 |
| 技术规范驱动的澄清 | 团队规范中隐含的需求前提 | 规范要求"所有列表页必须支持分页"，PRD 有列表但没提分页 → 自动生成澄清问题 |
| 全局需求检查清单 | 团队维护的全局需求标准项 | 登录体系、权限模型、错误处理、埋点、性能指标，逐项检查 PRD 是否覆盖 |
| 非功能需求常见项 | 不同项目类型的 NFR 基线 | C 端项目需要兼容性到 iOS12，B 端项目只需要 Chrome 最新两版 |
| 历史方案的技术约束 | 之前类似方案的局限性 | 某功能用 WebSocket 实现时有连接数限制，需求阶段就要明确并发量 |

**实现流程**：
```
PRD 文本
  ↓
LLM 分析 PRD，提取功能模块关键词（如"头像上传""列表页""登录"）
  ↓
用关键词检索知识库：
  - 历史需求文档 + 澄清问题记录
  - 团队技术规范中相关条目
  - 全局需求检查清单
  ↓
检索结果（top 5-8 条）作为"参考问题"注入 prompt
  ↓
LLM 结合 PRD + 参考问题，生成当前需求的澄清问题清单
```

关键点：
- **全局需求检查是程序化的**，不靠 LLM——知识库维护一个结构化 checklist，逐项匹配 PRD 中是否有相关描述，缺失的自动加入澄清问题
- 历史澄清问题是**参考**，不是照搬——LLM 需要判断当前 PRD 是否已经覆盖了这些问题
- 检索 query 由 LLM 动态生成（查询时动态增强）

### 阶段2：用户故事拆解

**核心价值**：用历史优秀案例做参照系，提升故事拆解质量。

| 使用场景 | 知识库提供什么 | 举例 |
|---|---|---|
| 历史类似需求的故事结构 | 同类功能通常拆成哪些故事 | "登录注册"模块通常拆成：手机号登录、验证码登录、注册、忘记密码、第三方登录 |
| AC 写法模式库 | 不同类型功能的 AC 常见写法 | 表单类功能的 AC 通常包含：必填校验、格式校验、长度限制、重复提交、成功跳转、失败提示 |
| 团队故事规范 | 故事大小、AC 数量、异常场景要求 | 每个故事不超过 3 天工作量、至少 1 条正常 AC + 1 条异常 AC |
| 依赖关系模式 | 同类功能中故事间的常见依赖 | "修改密码"依赖"登录"，"头像上传"依赖"个人信息页" |

**实现流程**：
```
结构化需求（含功能点列表）
  ↓
按功能模块检索历史故事集
  ↓
检索到的历史故事作为"参考结构"注入 prompt（不是照搬，而是告诉 LLM "这类功能通常这么拆"）
  ↓
LLM 结合当前需求生成故事 + AC
  ↓
程序化质量检查：AC 数量、异常场景覆盖、可测试性（知识库中的故事规范作为检查规则）
```

关键点：
- 这个阶段知识库的作用**比澄清阶段弱**——故事拆解更多依赖当前需求本身，知识库只是提升质量的参考
- 按**功能模式**分类检索：表单类、列表类、详情类、流程类、设置类，每类维护一个拆解模板

### 阶段3：技术方案设计

**核心价值**：复用已有成果，避免重复造轮子，确保方案符合团队规范。这是知识库价值最大的阶段。

| 使用场景 | 知识库提供什么 | 来源 |
|---|---|---|
| API 契约复用 | 历史类似功能的接口定义 | 代码反解析（api 目录）+ 接口文档 |
| 组件复用 | 现有组件库的组件和 props | 代码反解析（组件源码）+ 组件文档 |
| 技术方案参考 | 历史类似功能的架构决策 | 已合并 PR 描述 + 历史方案文档 + 技术 wiki |
| 代码规范遵循 | 目录约定、命名规范、写法约定 | 规范文档 + 配置文件 |
| 异常处理模式 | 请求重试、错误提示、loading 管理 | 代码反解析（全局拦截器、hooks）+ 规范文档 |
| 状态管理方案 | 全局状态 vs 局部状态的划分惯例 | 历史方案 + 规范文档 |

**实现流程**：
```
用户故事 + Figma + 项目信息
  ↓
阶段内多次按需检索（不是一次性检索全部）：
  - 设计 API 时 → 检索 API 接口
  - 设计组件时 → 检索组件库
  - 设计架构时 → 检索历史方案
  - 检查规范时 → 检索代码规范
  ↓
检索结果分类注入 prompt：
  - "可复用的 API" → 优先使用，标记"复用"
  - "可复用的组件" → 方案中直接引用
  - "参考方案" → 作为设计参考，不照搬
  - "规范约束" → 方案必须遵循
  ↓
LLM 生成技术方案，标记哪些是复用、哪些是新增
  ↓
API 契约确认（硬卡点）
```

### 三阶段对比总结

| 维度 | 需求澄清 | 故事拆解 | 技术方案设计 |
|---|---|---|---|
| 知识库作用 | 补全澄清盲区 | 提升故事质量 | 复用已有成果 |
| 重要性 | 中（增强） | 低（参考） | 高（核心输入） |
| 检索内容 | 历史澄清问题、规范、全局需求清单 | 历史故事结构、AC 模式 | API、组件、方案、规范 |
| 注入方式 | 参考问题 + 程序化检查 | 参考结构 + 程序化检查 | 分类参考 + 约束 |
| 检索时机 | 阶段开始时一次 | 阶段开始时一次 | 阶段内多次按需 |
| 没有知识库会怎样 | 澄清问题可能不全面 | 故事质量依赖 LLM 本身 | 重复造轮子，方案可能不符合规范 |

## 检索机制

### 整体检索架构

采用**混合检索 + 查询时动态增强**，不是纯向量检索。检索由 **Agent 内部自主执行**（ADR-014：DesignAgent/CodingAgent 在 retrieveKnowledge 中通过 BaseAgent.searchKnowledge helper 调用 KnowledgeService；ContextManager 不做预检索，只做产物装配）：

```
当前阶段的任务上下文
    ↓
LLM 动态构造多检索 query（查询时增强）
    ↓
┌─────────────────────────────────────┐
│  多路并行检索                        │
│  ├─ 关键词精确检索（BM25）           │
│  ├─ 向量语义检索（pgvector）         │
│  └─ 元数据过滤（类型/业务域/技术栈）  │
└─────────────────────────────────────┘
    ↓
合并去重（按知识 ID 去重，保留最高分）
    ↓
Rerank（LLM 二次筛选，判断与当前任务的实际相关性）— v2
    ↓
Top N 结果（通常 5-10 条）
    ↓
按类型分类，注入对应阶段的 prompt
```

### 为什么不用纯向量检索

| 场景 | 纯向量的问题 | 混合检索的优势 |
|---|---|---|
| 查具体接口名（如 `getUserInfo`） | 向量可能匹配到语义相近但名字不同的接口 | 关键词精确命中 |
| 查"类似列表页的方案" | 关键词可能匹配不到 | 向量语义匹配 |
| 查"React 项目的状态管理方案" | 可能返回 Vue 的方案 | 元数据过滤技术栈 |
| 检索结果 top 20 中有一半不相关 | 直接注入浪费 token | Rerank 筛掉不相关的 |

### 检索结果的处理

检索到的知识不是直接塞进 prompt，需要做结构化处理和分类标注：

| 标注类型 | 含义 | prompt 中的处理方式 |
|---|---|---|
| 【可复用】 | API 接口/组件，可直接使用 | 优先使用，方案中标记"复用已有" |
| 【参考】 | 历史方案/模式 | 作为设计参考，不照搬 |
| 【约束】 | 规范/标准 | 方案必须遵循 |
| 【待确认】 | 文档与代码不一致 | 标记"可能过时，需人工确认" |

### 检索质量的自我评估

每次检索后，LLM 评估检索结果的质量：
- 检索结果是否覆盖了当前任务的核心需求？
- 是否有明显不相关的结果？（反馈给 rerank 优化）
- 是否有缺失？（构造新 query 补充检索）

形成**检索-评估-补充检索**的小循环，最多 2-3 轮。

## 向量模型选型

### 选型对比

| 模型 | 维度 | 最大Token | 中文效果 | 部署方式 | 成本（每百万token） | 核心优势 | 核心劣势 |
|---|---|---|---|---|---|---|---|
| **Qwen3-Embedding**（通义） | 1024 | 32768 | ⭐⭐⭐⭐⭐ 最新SOTA | 阿里云API / 开源本地 | ~¥0.7 | 中文顶级、超长上下文、有开源版 | API依赖阿里云 |
| BGE-M3（智源） | 1024 | 8192 | ⭐⭐⭐⭐⭐ 开源标杆 | 本地部署 | 免费 | 中文好、支持混合检索、多语言 | 需GPU部署维护 |
| BGE-large-zh-v1.5 | 1024 | 512 | ⭐⭐⭐⭐⭐ 中文专用最佳 | 本地部署 | 免费 | 纯中文效果极佳、轻量 | 仅中文、文本短 |
| OpenAI text-embedding-3-small | 1536 | 8191 | ⭐⭐⭐ 中等 | API only | ~¥0.15 | 稳定、生态好、便宜 | 中文弱、需代理 |
| OpenAI text-embedding-3-large | 3072 | 8191 | ⭐⭐⭐⭐ 较好 | API only | ~¥0.95 | 精度高、MRL灵活 | 贵、中文仍不如国产、需代理 |

### 选型决策：通义 Qwen3-Embedding（API 版，1024 维）

**选择理由**：
1. **中文效果最新 SOTA**：2026 年发布的 Qwen3-Embedding 在 CMTEB（中文多任务嵌入基准）上排名前列
2. **32K 超长上下文**：技术方案文档不需要切太碎，保留完整上下文，检索更准确
3. **1024 维度**：pgvector 的甜点区，HNSW 索引性能好，存储成本合理
4. **国内访问稳定**：阿里云 API，不需要代理，团队级服务可靠性高
5. **成本低**：约 ¥0.7/百万 token，团队知识库全量重建一次成本极低
6. **有开源版**：后续如果不想依赖 API，可以用开源版本地部署，迁移成本低

**pgvector 维度选择 1024 的理由**：
- 1024 维是 pgvector 的甜点区，HNSW 索引性能好，区分度足够
- 3072 维存储和计算成本翻倍，pgvector 延迟明显增加
- 512 维区分度不够，中文场景召回率下降 10-15%

**备选方案**：如果团队有 GPU 服务器且不想依赖外部 API，可切换为 BGE-M3 本地部署，额外优势是支持稀疏向量检索，可减少对 BM25 的依赖。

## 维护机制

### 知识来源与入库流程

```
知识来源                    采集方式              解析方式
─────────────────────────────────────────────────────────
代码仓库（main分支）    →  webhook 触发/定时拉取  →  AST 反解析
飞书文档 wiki（v2）     →  API 定时同步          →  Markdown 解析 + 标题层级提取
历史 PR/方案文档        →  API 拉取               →  文本提取 + 元数据关联
人工录入（可选）        →  管理界面/CLI           →  结构化表单
                              ↓
                    质量校验（规则校验 + 交叉验证）
                              ↓
                    向量化（Qwen3-Embedding，1024 维）
                              ↓
                    入库（PostgreSQL + pgvector）
                              ↓
                    索引构建（关键词索引 + 向量索引 + 元数据索引）
```

### 飞书文档同步（v2）

技术文档 wiki 使用**飞书文档**，同步方式：

1. **配置飞书应用**：创建飞书自建应用，获取文档读取权限
2. **配置文档目录**：指定需要同步的飞书知识库/文件夹，支持增量同步
3. **定时同步**：每天一次全量同步，检测文档变更
4. **解析方式**：飞书文档 API 获取内容，按标题层级切分 chunk，标题路径作为天然标签（如"前端规范 > 代码风格 > 命名规范"）
5. **变更检测**：对比文档版本号，只重新解析变更的文档
6. **与代码交叉验证**：文档中提到的接口/组件，如果代码中不存在，标记"文档可能过时"

### 各知识类型的维护策略

| 知识类型 | 更新频率 | 更新方式 | 质量保证 |
|---|---|---|---|
| API 接口 | 高（代码每次变更） | 增量：只重新解析变更文件 | 与 OpenAPI 文档交叉验证，不一致以代码为准 |
| 组件用法 | 中 | 增量：组件文件变更时重新解析 | props 定义 vs 实际使用交叉验证 |
| 数据模型 | 中 | 增量：类型文件变更时重新解析 | 字段完整性校验 |
| 技术方案 | 低（PR 合并时） | 增量：新 PR 合并时入库 | 必须经过评审的 PR 才入库 |
| 代码规范 | 低 | 全量：规范文档变更时重建 | 人工审核 + 规则校验 |
| 飞书文档 wiki | 中 | 定时同步（每天一次） | 与代码交叉验证，标记"可能过时" |
| 历史澄清问题 | 低（需求冻结时） | 增量：每个需求完成后入库 | 需求评审通过的才入库 |

### 增量更新机制

```
代码仓库变更（webhook 触发）
    ↓
获取变更文件列表
    ↓
按文件类型分类：
  - api/*.ts → 重新解析 API
  - components/*.tsx → 重新解析组件
  - types/*.ts → 重新解析数据模型
  - 其他 → 跳过或标记"需评估"
    ↓
对变更文件重新解析，生成新知识
    ↓
与旧知识对比：
  - 新增 → 入库
  - 修改 → 更新版本，旧版本标记"已过时"
  - 删除 → 标记"已移除"，不物理删除
    ↓
重新向量化变更的知识
    ↓
更新索引
```

关键点：**不物理删除知识**，只标记状态（active/过时/已移除）。检索时默认只查 active，需要历史对比时可以查旧版本。

### 质量保证体系（五层）

| 层级 | 机制 | 实现方式 |
|---|---|---|
| 第一层：来源过滤 | 只从可信来源采集 | 配置白名单：main 分支、已合并 PR、官方文档仓库、指定飞书知识库 |
| 第二层：交叉验证 | 多来源互相比对 | 代码 vs 文档、定义 vs 使用，不一致标记"存疑" |
| 第三层：规则校验 | 程序化检查完整性 | API 必须有 method/路径/参数/响应；组件必须有 props 定义 |
| 第四层：使用反馈 | 被引用后的结果反馈 | 方案评审通过 → 提升权重；CR 打回因知识有误 → 降低权重 |
| 第五层：过期检测 | 长期未被引用或来源已删除 | 90 天未被引用 → 降权；来源代码已删除 → 标记"已移除" |

### 权重系统

每条知识有一个动态权重（0-1），影响检索排序：

```
初始权重 = 来源可信度（main分支=1.0, 已合并PR=0.9, 文档=0.8）

权重调整：
+ 被方案引用且评审通过  → +0.1（上限1.0）
+ 被多次引用            → +0.05/次（上限1.0）
- 被引用后 CR 打回      → -0.2
- 与代码不一致          → -0.3
- 90天未被引用          → -0.1/月（下限0.1）
- 标记"已移除"          → 不参与检索
```

### 冷启动策略

新项目/新团队没有历史知识时：

1. **内置通用基线**：前端通用最佳实践（React/Vue 通用模式、常见组件设计、状态管理惯例）作为初始知识库
2. **快速积累**：第一个项目完成后，自动把该项目的方案、API、组件入库
3. **人工补充**：团队可以通过管理界面或 CLI 手动录入重要的技术文档和规范
4. **渐进式**：前几个项目知识库作用有限，但随着项目积累，检索质量会提升

## 与现有代码索引的关系

- 共用检索基础设施（向量库、AST 解析、embedding 模型）
- 数据分开存储：知识库是团队级，代码索引是项目级
- 检索时同时查：知识库给通用模式，代码索引给项目特定实现
- 不要把项目特定代码混进通用知识库
